00Method and what was observed

The review is grounded in three sources: a full read of the Rust sources and the shell hooks, a scripted tmux session that drove the installed 0.3.3 binary through 41 states with an isolated HOME and XDG_DATA_HOME, and an inspection of the real data directory.

What works well today. Byte-transparent passthrough (no alt-screen, native scrollback and selection survive), the draft is never lost, dangerous actions need a second press, conditional execution is visible per item, the hints row adapts to width, alt-screen and mouse-capture programs are handed the screen automatically, and the PTY test suite is unusually thorough. The improvements below build on that foundation rather than replace it.
Where the friction is. The product is invisible until a command runs longer than 1.5 s; state is communicated by single glyphs (▶ ○ ✓ ✎ ↑); four different keys flip who owns the keyboard; the panel changes height (and resizes the child PTY) every time an item is added; there is no completion, no history, no notification when the queue finishes, no way to enqueue from outside the panel, and no configuration surface at all.

Evidence that shaped the list

  • Panel height churn. desired_layout (app.rs:1949) recomputes height from queue length and notice presence; any change goes through transition_layout (app.rs:2026) which releases, re-reserves, and calls resize_pty_for_layout. Adding one queued item therefore sends the running program a SIGWINCH.
  • Same label, different key. While a command runs the hint reads F2 ↑ Type above; at an idle or paused prompt the identical label is bound to Ctrl-Q (captures 01 vs 14).
  • Persistent chrome at an idle prompt. After Ctrl-KCtrl-K at a prompt the panel stays reserved showing "↑ Typing above" plus the "Cleared 12 commands" notice until F3 is pressed (capture 22), because panel_should_be_visible (app.rs:265) includes activity.is_some().
  • Overflow without a count. Twelve queued items render as "○ ↓" with eight rows and no indication of how many are hidden (capture 18); header_reports_hidden_queue_items in panel.rs asserts the count is not shown.
  • Quit discards silently. The pending-quit hint says "Ctrl-D Quit (press again)" while the status that explains the queue will be discarded is suppressed by panel_notice (capture 40).
  • Readline prefix leak. Ctrl-X at an idle prompt with an empty queue is forwarded as byte 0x18, which Bash treats as a chord prefix; the next typed character is swallowed (capture 27: leep 2).
  • Dead restore path and leaked directories. new_session_path (queue.rs:737) always creates a fresh directory, so prepare_queue_for_startup (app.rs:1635) can never find items to restore, and nothing removes queues/<pid-ts>/ on exit: 21 orphaned directories were present on the machine used for this review.
  • Idle I/O. Every session reads and locks its own queue file every 500 ms (sync_queue_from_disk_if_due) and rewrites a lease file every second (refresh_session_lease_if_due), although no other process writes those files.
  • Tab message is a leftover. Tab in the editor says "Completion is not available in the queue — Alt-S changes the run condition"; the second clause dates from when Tab toggled the condition.

AFirst run and discoverability

cmdq is deliberately invisible until a command has run for 1.5 seconds. That is the right default for experienced users, but it means a new user sees a bare prompt and has no way to know whether cmdq is working, broken, or even running. These four items make the first ten minutes self-explanatory without adding chrome to the steady state.

01

One-time startup line so users know cmdq is active

featureeffort Simpact ●●●●○

Problem

Capture 00 is a bare $. Nothing distinguishes a cmdq-hosted shell from a plain one. The README explains the 1.5 s rule, but the product never does, and the only in-app discovery path is pressing F1 while a panel happens to be visible.

Proposal

Print one dim line before the shell's first prompt, and only on the first few launches (or until the user has queued something once): cmdq 0.3.3 · the queue opens when a command runs ≥1.5 s or on Ctrl-Q · F1 help. Suppress with CMDQ_QUIET=1 or the config key startup_hint = false (item 33). After the first successful dispatch, write a marker file so the line never appears again.

Where

  • src/app.rs · run_with_exit_status (app.rs:581), just before ShellPty::spawn: write the line to stdout with the same dim attribute the panel uses, followed by \r\n, so the shell's prompt lands under it.
  • src/paths.rs: add state_dir() ($XDG_STATE_HOME/cmdq or the data dir) and a first_run_marker() path.
  • src/app.rs · dispatch_next_eligible (app.rs:2435): on the first Claimed dispatch, touch the marker.

How

  1. Before spawning, check the marker; if absent and not quiet, emit the line. Do this before raw mode so the terminal's own line discipline handles wrapping.
  2. Ask the terminal for the cursor position after the line (the existing query_cursor_position already runs after raw mode is enabled) so the initial panel reservation math stays correct.
  3. Rate-limit: show on at most the first three launches even if nothing is ever dispatched, so a user who only ever runs quick commands is not nagged forever.

Tests

tests/binary_smoke.rs: new session with empty state dir prints the line once; a second launch after a dispatch prints nothing; CMDQ_QUIET=1 prints nothing. Assert the prompt still appears on the row below the line (cursor query path).

02

Integration health check in-session and cmdq --doctor

featureeffort Mimpact ●●●●●

Problem

If the OSC 133 markers never arrive (a prompt framework that replaces precmd, a .zshrc that execs another shell, an instant-prompt cache, a stray trap DEBUG), cmdq silently degrades to a transparent wrapper: no panel ever appears and every keystroke goes to the shell. The user's only signal is absence. There is also no way to ask "is my setup healthy?" from the command line.

Proposal

Two layers. In-session: track "Enter pressed at the prompt with a plausible command" (the app already computes submitted_prompt_line) versus "CommandStart marker received". If three submissions pass with no marker, set a sticky warning: shell hooks are not reporting — queueing is off · run cmdq --doctor. CLI: cmdq --doctor spawns the user's shell in a PTY exactly as a session would, runs true, and reports which markers were seen, which shell and rc files were used, whether the terminal answered the cursor query, whether Alt sends ESC-prefixed bytes, and the data-dir state (orphaned queues, lock files). Exit non-zero when hooks are missing.

Where

  • src/main.rs: add --doctor to Cli; dispatch to a new src/doctor.rs.
  • src/doctor.rs (new): reuse ShellPty::spawn (pty.rs) and osc133::Detector::for_cmdq; feed output for up to 3 s; print a checklist.
  • src/app.rs · AppState: add unconfirmed_submissions: u8; increment in should_optimistically_mark_command_started (app.rs:3355) when it returns true; reset to 0 in handle_osc_event on CommandStart.
  • src/app.rs · mark_command_started (app.rs:2361): if the optimistic start is never confirmed by a marker before the next PromptStart... there is no PromptStart either when hooks are missing, so use a timer: 2 s after an optimistic start with no marker, count it.

How

  1. Doctor output is plain text, one check per line with ✓/✗, followed by a remediation hint per failure (for example "powerlevel10k instant prompt detected: move the cmdq exec line above the instant-prompt block").
  2. In-session warning uses the sticky severity from item 10 so it does not fade after 4 s.
  3. Document in README under Troubleshooting: "Nothing appears? Run cmdq --doctor".

Tests

tests/shell_matrix.rs: doctor passes for bash, zsh and fish with clean homes; fails with a zshrc that unfunctions add-zsh-hook. Unit test in app.rs: three optimistic starts without markers set the warning; one marker clears the counter.

05

Stable panel height: stop resizing the child for every queued item

fixeffort Mimpact ●●●●●

Problem

panel_height (panel.rs:109) is 1 + min(queue.len, 8) + 1 + 1 + notice. Every enqueue, delete, notice appearance and notice fade changes the height; transition_layout releases the region, re-reserves it, and resizes the PTY, which delivers SIGWINCH to the running program. Progress bars redraw, less -X style pagers reflow, log tails jump, and the shell's cursor row is recomputed each time. Captures 03 → 04 show the input line moving down a row simply because a notice appeared.

Proposal

Introduce hysteresis and a reserved notice slot:

  • While a command is running, the panel may grow but never shrink; shrink only at CommandEnd or when the panel hides.
  • Grow in steps of two rows (2, 4, 6, 8 list rows) rather than one, halving resize events while composing a queue.
  • Always reserve the notice row while the panel is open; paint it blank when there is nothing to say (item 10).
  • Coalesce: if a layout change is requested twice within 100 ms, apply only the last (a burst of pastes or deletes becomes one resize).

Where

  • src/panel.rs · panel_height: accept a min_height floor from the caller; notice row always counted.
  • src/app.rs · desired_layout (app.rs:1949): new field AppState.layout_floor: u16; set to the current reserved height on every grow while shell_state == Running; reset to 0 in handle_osc_event on CommandEnd and when the layout becomes Hidden.
  • src/app.rs main loop step 2 ("Update panel layout"): add layout_change_requested_at: Option<Instant> for coalescing.

Tests

tests/path_a_smoke.rs: queue five items during sleep; count DECSTBM writes (find_decstbm helper exists) and assert at most three; after the sixth item is deleted the region height is unchanged until the command ends. Unit test: desired_layout never returns a smaller Reserved height than the floor while running.

08

Header shows the running command, elapsed time and batch progress

featureeffort Mimpact ●●●●●

Problem

The header is a single glyph (▶) and a rule. cmdq knows exactly which command is running (it dispatched it), when it started (command_started_at), how many it has dispatched in this batch, and how many remain. 09

Theme-safe rendering: attributes over absolute colours, NO_COLOR

fixeffort Simpact ●●●○○

Problem

The painter uses five absolute ANSI colours (Cyan, Yellow, Grey, DarkGrey, White). On a light-background terminal White (the first queued item) is invisible and Yellow notices are barely legible; on Solarized Light, Grey and DarkGrey invert. There is no NO_COLOR support and no way to adjust.

Proposal

Express hierarchy with attributes first (bold for the next item and the active hint key, dim for secondary items and labels, reverse video for the selected row) and use the terminal's default foreground. Keep two accent colours (state and warning) chosen from the 16-colour palette so they follow the user's theme, and honour NO_COLOR and TERM=dumb by dropping colour entirely. Expose the palette in the config file (item 33).

Where

  • src/panel.rs: introduce struct Palette { state, warn, accent, muted, selected } stored in PanelState; replace every SetForegroundColor(Color::…) in paint_normal, paint_header, paint_hints, paint_help.
  • src/app.rs · run_with_exit_status: build the palette from env and config once.

Tests

With NO_COLOR=1 the painted bytes contain no SGR colour parameters (30–37, 90–97, 38); with colour enabled, no absolute White is emitted.

10

One message model with severity, a fixed slot, and no input-line jumping

refactoreffort Mimpact ●●●●○

Problem

Feedback is split across status (fades after STATUS_TTL), activity (sticky until F3), hint-row overrides for pending confirmations, and a suppression list in panel_notice (panel.rs:60) that decides by string prefix which statuses are "routine". Consequences: errors such as "queue save failed" fade like chatter; the pending-quit explanation is hidden (capture 40); a sticky activity keeps the whole panel reserved at an idle prompt (capture 22); and the input line moves when a notice appears.

Proposal

Replace both strings with Option<Message> where Message { text, severity: Info | Success | Warning | Error, sticky: bool, set_at }. Rules: Info/Success fade after 4 s; Warning stays until the next user action; Error stays until F3 or resolution. Only one message shows at a time; a new Error preempts, a new Info does not replace a Warning. The notice slot is always reserved while the panel is open (see item 5) and painted blank when empty. A sticky message alone never keeps the panel open at an idle prompt; instead it is shown once the panel next appears, and a Warning/Error additionally prints a single dim line into the shell area when the panel hides so it is not lost.

Where

  • src/app.rs: new enum Severity, struct Message; replace status, status_set_at, activity in AppState; set_status (app.rs:321) becomes notify(severity, text); tick_status (app.rs:326) implements the fade rules; remove activity.is_some() from panel_should_be_visible (app.rs:265).
  • src/panel.rs: delete the prefix list in panel_notice; PanelState.message: Option<(&str, Severity)>; colour by severity via the palette (item 9).
  • Every set_status( call site (about 40) gets a severity; the routine ones ("added:", "saved:", "dispatched:") become Success and are shown in the notice slot for 2 s rather than suppressed, since the slot no longer costs a row.

Tests

Replace routine_feedback_is_quiet_but_errors_and_recovery_remain with: Error outlives 10 s of ticks; Info fades; a Warning is not replaced by an Info; the panel height is identical with and without a message; hiding the panel with a pending Error prints one line to the shell area.

CKeys, modes and confirmations

Who owns the keyboard is the central question of a PTY wrapper. cmdq answers it with six states and four toggles; users need one question ("queue or program?") and one key.

11

redesigneffort Mimpact ●●●●●

Problem

Four gestures move keystrokes between the queue and the terminal, each with slightly different scope:

KeyWhat it does todayWhere

Ctrl-QToggles force_queue at the prompt; forwarded to the program when the editor does not own inputapp.rs:2794

Where

  • src/app.rs · handle_key_with_bytes: delete the Esc-Esc block and the Ctrl-\ toggle branch; merge the F2 and Ctrl-Q branches into toggle_focus(state).

12

Meta-free and F-key-free alternatives, with macOS Option detection

fixeffort Simpact ●●●●○

Problem

Three core actions need Alt (Alt-S condition, Alt-U undo, Alt-↑/↓ reorder) and three need function keys (F1–F3). On a stock macOS Terminal or iTerm2, Option inserts ß, ¨, ˚; on a MacBook keyboard F-keys need Fn; inside some multiplexers F1 arrives as ESC O P and is mis-parsed. The README acknowledges the Option issue but the product cannot tell the user why Alt-S just typed a letter.

Proposal

Every action gets a Ctrl-only alternative and the hints show whichever the terminal is known to deliver:

Release checklists, deploy sequences and "morning routine" pipelines are the same five commands every time, and they are retyped every time.

Proposal

cmdq save <name> writes the current items (commands, conditions, no origins) to ~/.config/cmdq/queues/<name>.json; cmdq load <name> appends them, paused, with a Success message "loaded release (5) · Ctrl-X starts". In-panel: Ctrl-S on an empty draft prompts for a name in the input line; a draft starting with @ completes saved queue names (@rel Tab → @release) and Enter loads it. Saved queues are plain JSON so they can be committed to a repo and shared; a project-local .cmdq/queues/ is searched first.

Where

  • src/saved.rs (new): SavedQueue { name, items: Vec<{command, condition}> }, list/load/save with atomic writes.
  • src/cli.rs: save, load, queues subcommands.
  • src/input.rs: editor mode NamePrompt; @ completion hooks into item 16's completion state.
  • src/app.rs: load path reuses restore_removed_commands's "append paused" behaviour.

Tests

saved.rs round-trip; app.rs: @release Enter appends five paused items; binary_smoke: cmdq save x then cmdq load x in a fresh session.

foundationeffort Mimpact ●●●●○

Problem

Twelve tuning constants live at the top of app.rs (panel delay 1.5 s, eight visible rows, 4 s status fade, confirmation windows) and every key is a literal in handle_key. Users on slow CI-like commands want a longer delay; users who queue constantly want zero delay; people with terminals that eat Ctrl-Q or Alt need to rebind; light-theme users need colours. 34

Make input-ownership decisions transparent and loggable

diagnosticseffort Simpact ●●●○○

Problem

Whether a keystroke goes to the queue or the program depends on a termios check (needs_direct_input, pty.rs), a 200-character output-tail heuristic (looks_like_input_prompt, app.rs:458), alt-screen and mouse sniffing, and a 100 ms settling delay. When it guesses wrong the user experiences "my typing disappeared" or "the queue captured my password answer" and has no way to see why. env_logger is wired to stderr, which is the terminal itself, so logging is unusable during a session.

Proposal

Route logs to a file when CMDQ_LOG=<path> (or CMDQ_LOG=1 for the state dir) is set, and log every ownership transition with its reason: input → program (termios: ECHO off), input → program (tail matched "Password:"), input → queue (CommandEnd). In the panel, when focus is on the program because of a heuristic, the input line names the reason briefly: ↑ program is reading input (Password:) · Ctrl-Q for queue. cmdq --doctor (item 2) prints the log location.

Where

  • src/main.rs: configure env_logger with a file target when CMDQ_LOG is set.
  • src/app.rs · refresh_auto_passthrough_for_child_modes (app.rs:2312), update_child_input_detection (app.rs:2290), tty_input_requested: log::info! with the reason; store AppState.input_owner_reason: Option<&'static str> for the panel.
  • src/panel.rs · input_line: append the reason when present and width allows.

Tests

app.rs: a tail of "Password:" sets the reason string; CommandEnd clears it. binary_smoke: with CMDQ_LOG set, the file contains at least one transition line after a read -p command.

Message copy: one voice, one key spelling, no leftovers

polisheffort Simpact ●●●○○

Problem

Messages mix styles: "queue paused" (lower-case fragment), "Ctrl-C detected — queue paused. Ctrl-X to resume, Ctrl-K to clear." (sentence with period), "Cleared 12 commands — Alt-U restores paused" (verb first), "clear 3 queued commands? press ^K again to confirm" (caret notation). Keys appear as Ctrl-X in hints and ^X in statuses. The Tab message still advertises Alt-S. Glyphs ○ and ↑ in the header have no legend outside help.

Proposal

Adopt a four-rule style and apply it in one pass over the roughly forty set_status/activity sites: (1) outcome first, then the next action, separated by a middle dot: Queue paused · Ctrl-X resumes; (2) keys always spelled as in the hints row, generated from the binding table so renames propagate; (3) sentence case, no trailing period, at most 70 columns before the action clause so the outcome survives clipping; (4) name the thing acted on: "Removed make test", "Skipped git push". Replace header glyphs with words at ≥ 60 columns (running / paused / building / editing / terminal) and keep glyphs only for narrow widths.

Where

  • src/app.rs: every set_status( and activity = Some(; the Tab message in the CompletionUnavailable arm is deleted by item 16 anyway.
  • src/panel.rs · paint_header (panel.rs:456): width-aware word/glyph choice.
  • tests/: string assertions in binary_smoke and app.rs tests updated in the same commit; a new unit test asserts no status string contains ^ followed by a capital letter.

Small-terminal behaviour that explains itself

edge caseeffort Simpact ●●○○○

Problem

Below 5 rows or 20 columns the panel is disabled (terminal_allows_panel, app.rs:1631) and typing goes to the shell. The only message, "terminal too small for queue panel", appears if the user presses Ctrl-Q; a queue built before the shrink keeps dispatching invisibly, and on a paused queue only Ctrl-X/Ctrl-K work with no visible hint (capture 38). Split panes in tmux and small popups hit this regularly.

Proposal

When the panel is suppressed by size and the queue is non-empty or paused, print one dim line in the shell area on the transition ("cmdq: 3 queued, panel hidden (terminal 100×4) · Ctrl-X resume, Ctrl-K clear") and again when the size allows the panel back. Lower the floor to 3 rows by using the compact layout from item 6 automatically. Treat COLUMNS < 20 the same way.

Where

  • src/app.rs · the CtEvent::Resize arm: compare terminal_allows_panel before and after; emit the line through stdout at the tracked cursor.
  • src/app.rs · desired_layout: choose compact when term_rows < 8.

Tests

path_a_smoke tiny_terminal_does_not_reserve_invisible_panel extended: with two items queued the shrink emits the hint line exactly once; growing back re-reserves the panel and emits the return line.
